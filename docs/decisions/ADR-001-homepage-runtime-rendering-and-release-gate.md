# ADR-001: Главная рендерится только после запуска CMS, а релиз завершается проверкой содержимого

## Статус

Принято — 2026-08-09.

## Контекст

Во время `docker compose build` контейнер Directus недоступен по дизайну. Раньше главная страница использовала ISR и Next.js сохранял результат build-time рендеринга. При недоступной CMS этим результатом становилась заглушка «Каталог временно обновляется».

Скрипт релиза должен был удалить этот файл и прогреть страницу после запуска контейнеров. Однако его остановила ошибка применения Caddy-конфигурации: в Caddy включён `admin off`, поэтому hot reload через порт 2019 невозможен. Фронтенд уже был заменён, а прогрев и проверка содержимого не были выполнены.

## Решение

1. Главная страница экспортирует `dynamic = "force-dynamic"`. Она не создаёт статический HTML во время Docker-сборки и впервые получает данные только из работающего контейнера, который видит Directus.
2. Изменение Caddy применяется пересозданием только контейнера Caddy (`docker compose up -d --force-recreate caddy`), а не запросом к отключённому admin API.
3. `deploy/deploy.sh` остаётся единственной процедурой публикации. Успешным считается только его завершение с кодом 0.
4. После каждого релиза необходимо проверять именно публичный HTML `https://deere-shop.ru/`: в нём не должно быть строки «Каталог временно обновляется». HTTP 200 сам по себе не является доказательством успешного релиза.
5. Агент или разработчик не сообщает «выложено» до фиксации результатов: health frontend, health Caddy, публичный HTML без заглушки, проверка редиректов и 404.

## Последствия

- Главная получает CMS-данные на каждый запрос; это предпочтительнее публикации ложной страницы при недоступности CMS на этапе build.
- Временная недоступность Directus после запуска всё ещё может показать заглушку, но это уже реальная авария CMS, а не артефакт сборки. Скрипт деплоя останавливается и сообщает об этом вместо ложного успеха.
- Перед любым последующим релизом обязательны локальные `test`, `typecheck`, `lint`, `build`; после — проверки содержимого, а не только статусов HTTP.

## Контрольный список публикации

1. Выполнить локальные проверки и получить зелёный результат.
2. Отправить ровно проверенный коммит в GitHub.
3. На VPS выполнить `git pull --ff-only`, `git lfs pull`, затем только `sudo bash deploy.sh`.
4. Не продолжать, если скрипт завершился ошибкой; сначала устранить её и повторить весь скрипт.
5. Проверить `https://deere-shop.ru/` поиском строки заглушки, затем открыть страницу в мобильном браузере.
6. Проверить `404` для несуществующего адреса и `301` для `www` и `/index.html`.
7. Только после всех пунктов сообщать о завершении релиза.
