## 7. Найденные причины текущих проблем

### Массовая форма на главной

`frontend/src/app/HomePageView.tsx` сейчас рендерит `HomePartsRequest` между категориями и товарами. Именно это отодвигает каталог вниз. Отдельного маршрута `/parts-request` пока нет.

### Неработающие hero-ссылки

В `frontend/src/components/sections/HeroPartSearch.tsx` все три действия сейчас имеют одинаковый `href="#parts-request"`:

- «Вставить список»;
- «Загрузить Excel»;
- «Отправить фото».

Они только прокручивают к форме и не выбирают нужный режим загрузки.

### Исчезновение избранных товаров

`frontend/src/components/sections/HomeFeatured.tsx` скрывает карточки, если отсутствует хотя бы одно из полей:

- изображение;
- title/SKU;
- фиксированная цена;
- числовое значение цены;
- `deliveryStatus`.

А `getFeaturedProducts` применяет похожую строгую фильтрацию на уровне Directus. Поэтому весь блок возвращает `null`, когда у товаров не заполнены коммерческие поля.

Рекомендуемое исправление: показывать до пяти CMS-выбранных товаров при наличии изображения, названия и SKU; неизвестные цену/доставку не выдумывать. Для цены использовать существующий статус «по запросу», неизвестную доставку не выводить. Не скрывать весь раздел из-за необязательных коммерческих полей.

### Гигантские категории и отступы

В `frontend/src/app/globals.css` накопились поздние дублирующие overrides для категорий, product grid и responsive-режимов, особенно в областях около строк 4721, 4921–5005 и 5470–5550. Их нужно консолидировать, иначе более ранние компактные значения перекрываются поздними правилами.

Цель для карточки категории:

- desktop/tablet: 72–80 px;
- иконка: 36–40 px;
- название максимум две строки;
- без описания;
- touch-target не меньше 44×44 px.

### 15.4 Стабилизация тестов (4 августа)

При массовом запуске под конкурентной нагрузкой vitest падал с `JavaScript heap out of memory` (краш воркера jsdom + React 19). Причина — окружение, не код. Применены минимальные правки конфигурации без изменения тестов:

- `frontend/vitest.config.ts`: `maxWorkers: "50%"`, `minWorkers: 1` — ограничивает параллелизм воркеров.
- `frontend/package.json`: добавлен `npm run test:ci` с `--max-old-space-size=4096` для CI/тяжёлых окружений.
- Результат: набор стал стабильным и в ~2 раза быстрее (16.5s → 7.2s на 32 ядрах). Обычный `npm test` не изменился.

## 16. Уведомления менеджеру на почту (4 августа 2026)

Реализована отправка email-уведомления менеджеру при поступлении нового лида/заявки. Ранее это было отложено (п.15.5) — теперь готово.

### 16.1 Как это работает

- После успешного сохранения лида в Directus (`api/leads/route.ts`) сервер best-effort отправляет письмо менеджеру через SMTP (`nodemailer`).
- Уведомление **опционально**: если SMTP-env не задан — письмо тихо пропускается, лид всё равно сохраняется. Логика повторяет Turnstile (без секрета — выключено). Ничего не ломается, пока env не настроен.
- Сбой почты **никогда не влияет** на ответ клиенту: даже если SMTP недоступен, заявка получает `201 Created`. Ошибка пишется в лог сервера (`console.error`).
- Письмо содержит: имя, телефон, email, сообщение, продукт, категорию, страницу, список запчастей (артикул + кол-во), кол-во вложений, UTM. Вложения доступны в админке Directus (в письме только количество, чтобы не тянуть бинарники через почту).

### 16.2 Файлы

- `frontend/src/lib/notifications/env.ts` — валидация опциональных SMTP-env + `isNotificationsEnabled()`.
- `frontend/src/lib/notifications/notify.ts` — `notifyNewLead()`: формирует plain-text + HTML, отправляет через nodemailer.
- `frontend/src/lib/notifications/render.ts` — `renderLeadEmail()`: self-contained HTML-письмо с inline-стилями.
- `frontend/src/app/api/leads/route.ts` — вызов `notifyNewLead` после `createLead`.
- Тесты: `notify.test.ts` (5), `render.test.ts` (5), `env.test.ts` (4), `route.test.ts` (+2).

### 16.3 Что нужно настроить на production

Почта домена `cmteh.ru` обслуживается на **Яндексе** (MX → `mx.yandex.net`). Используется SMTP Яндекса, порт 465 (implicit TLS). Ящик `info@cmteh.ru` — одновременно отправитель и получатель уведомлений.

Добавить в `/opt/jd-landing/.env` (и перезапустить frontend-контейнер):

```text
SMTP_HOST=smtp.yandex.ru
SMTP_PORT=465
SMTP_SECURE=true
SMTP_USER=info@cmteh.ru
SMTP_PASSWORD=пароль-приложения-Яндекса
SMTP_FROM=info@cmteh.ru
NOTIFY_EMAIL_TO=info@cmteh.ru
```

**КРИТИЧНО — пароль приложения:** `SMTP_PASSWORD` должен быть **паролем приложения** из настроек Яндекс ID, а НЕ основным паролем ящика. Яндекс запрещает SMTP-авторизацию основным паролем. Создаётся так: Яндекс ID → Безопасность → Двухфакторная защита (включить, если выключена) → Пароли приложений → Создать → тип «Почта». Полученную 16-значную строку вставить в `SMTP_PASSWORD`.

Проверка после настройки: отправить тестовую заявку с сайта — письмо должно прийти на `info@cmteh.ru`. Если не пришло — смотреть `docker compose logs frontend` на `[notifications] lead email failed`.

Если основной ящик `info@cmteh.ru` жалко использовать для рассылки, альтернатива: создать в Яндексе отдельный ящик (например `notify@cmteh.ru`), указать его в `SMTP_USER`/`SMTP_FROM`/`SMTP_PASSWORD`, а `NOTIFY_EMAIL_TO` оставить `info@cmteh.ru` — тогда отправитель один, получатель другой.

## 18. Замеченный, но не чиненный дефект

При написании тестов обнаружено: `leadSchema` (zod 4) с конфигурацией `email`-поля (`z.union([z.email(), z.literal(""), z.undefined()]).transform(...)`) помечает `email` как **обязательное** — заявка без email получает 400. Это pre-existing поведение, не связано с уведомлениями. Заявка без email реалистична (чаще только телефон). Решить отдельно — это самостоятельная задача валидации формы, не уведомлений.
