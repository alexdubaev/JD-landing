## Подтверждённые проблемы и план

### 1. Старый AH140497 не перенаправляется

Старый адрес:
`/catalog/sistema-ohlazhdeniya-i-vpusk/tsentralnyy-shkiv-john-deere-ah140497`.

Действующий адрес:
`/catalog/remni-tsepi-i-shkivy/tsentralnyy-shkiv-john-deere-ah140497`.

До исправлений production возвращал 200, отсутствующий canonical, `noindex` и
`NEXT_HTTP_ERROR_FALLBACK;404`. Это подтверждено также запросами с User-Agent
YandexBot и Googlebot. HTTP Location отсутствует.

AH140497 включён в точную карту исторических адресов. Нормализация в
`proxy.ts` возвращает **301** непосредственно на действующую карточку,
сохраняет параметры кроме первой страницы и не меняет действующий URL.
Старое правило в `next.config.ts` заменено общей проверенной реализацией
нормализации, чтобы исключить цепочку и цикл `page=1`.

### 2. Чрезмерная глубина последовательной пагинации

`Pagination.tsx` отдаёт только предыдущую и следующую страницы. Ссылки есть
в серверном HTML; проблема — число последовательных переходов. Это не
доказательство причины исключения карточек из поиска.

Исправление: на `/catalog` добавлен компактный раскрываемый HTML-индекс
всех категорий из CMS; в общей и категорийной пагинации — такой же индекс
с прямыми ссылками на **все** страницы. Используется нативный `<details>`:
ссылки находятся в серверном HTML без JavaScript. Prefetch для всех номеров
отключён. Существующие URL, поиск и фильтры сохранены.

Через общий каталог путь до любой карточки ограничивается тремя переходами:
главная → каталог → нужная страница → карточка. Для карточек первой страницы
нужны два перехода. Это проверяется по якорям и полноте товарного списка,
а не по присутствию URL в sitemap.

### 3. Цикл нормализации `page=1`

До исправлений `GET /catalog?page=1` возвращал 308 с тем же Location;
старое общее правило также зацикливало URL карточек с `?page=1`.

Исправление в `normalize-url.ts` и `proxy.ts`: для GET/HEAD первой страницы
общего/категорийного списка удаляется `page`, остальные параметры, включая
повторяющиеся UTM, сохраняются. Используется первый `page`, как в разборе
параметров каталога. Если первый `page=2`, а следующий `page=1`, редиректа нет.
Исторические URL получают один 301 сразу на очищенный действующий URL.
Для действующей карточки `?page=1` больше не вызывает прежний общий цикл.

### 4. Документированное объединение категорий не даёт публичного редиректа

История Directus проверена read-only через PostgreSQL. Найдены **62**
уникальных старых адреса опубликованных товаров, которые отличаются от
действующих адресов. Независимое восстановление последовательности изменений
slug/category подтвердило тот же набор. История создания, назначения первой
категории и повторные записи не считаются переносом.

Все 62 старых адреса до исправлений отвечали 200 с noindex, без canonical и
без перенаправления. Все 62 конечных адреса отвечали 200 с canonical на себя
без запрета индексирования. Карта `legacy-product-redirects.json` содержит
эти 62 точные пары и отдельно подтверждённое объединение категории
`/catalog/krepezh-i-krepleniya` → `/catalog/krepezh` (итого 63 правила).
Текущих URL среди источников и цепочек между правилами нет. Неизвестные товары
не перенаправляются на категорию или главную.

## Canonical, robots и lastmod

`robots.txt` разрешает публичный каталог и карточки, закрывает `/api/`,
`/thank-you`, `/parts-request`, указывает корректный sitemap. Проверенные
`/catalog?page=55`, `?page=320` и категория с `?page=2` имеют self canonical
и разрешены к индексации. Поиск `?q=AH140497` возвращает `noindex, follow`
и canonical на каталог. Параметры `verify` и `audit_live` в проверенных
примерах canonical не меняют. Noindex страницы ошибки не следует снимать.

В sitemap 12 997 дат lastmod и 7 страниц без даты. Неверных или будущих дат
нет. Даты: 10 августа — 16, 13 августа — 2, 18 августа — 299,
23 августа — 12 680. Последняя дата — `2026-08-23T18:34:04.313Z`.
Отсутствие необязательного lastmod у основных страниц само по себе не ошибка.

Sitemap берёт `products.updated_at` и `categories.updated_at`; схема задаёт
автоматическое `date-updated`. Августовская дата не доказывает устаревание.
Изменение связанного файла, характеристики или другого дочернего объекта
может не обновить родительскую запись: это риск, а не подтверждённый случай
неверной даты. Для подтверждения нужно сопоставить фактические изменения
контента и историю CMS; не подставлять текущую дату во весь sitemap.

С доступом владельца выполнена read-only сверка всех 12 971 опубликованной
карточки: набор URL совпадает с sitemap; **расхождений lastmod с updated_at
нет**. После августа есть изменения связанных файлов (07.10, конвертация
изображений в WebP), но это не подтверждает изменение основного содержания
карточек и не оправдывает массовую установку сегодняшней даты. Даты, robots,
canonical, данные CMS и содержимое карточек не менялись.

Compose и временный override только build context фронтенда на чистый checkout;
образ собирается и `up -d --no-deps frontend` заменяет только магазин. Текущий
образ сохраняется для отката; конфигурации остальных сервисов сверяются.

CMS, публичная приёмка 63 редиректов, метаданных, полный обход HTML-графа и
визуальная проверка каталога.

Чужое изменение production Caddyfile для другого сервиса не включается в
SEO-релиз, не перезаписывается; Caddy, CMS, базы и другие сервисы не
перезапускаются. До начала операции сохраняется его копия и проверяется hash.

Визуальная локальная проверка при 1365 и 390 px: категории раскрываются,
