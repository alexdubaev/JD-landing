# Автономная русскоязычная админка Directus

## Цель

Превратить Directus из технического перечня таблиц в самостоятельный центр управления сайтом, который можно передать клиенту. Клиент должен менять содержимое, изображения, контакты, каталог, SEO и состав главной страницы без правок фронтенда.

## Критерии готовности

- Интерфейс проекта Directus, названия коллекций, полей, вариантов выбора, подсказки и пользовательские ошибки отображаются на русском языке.
- Основная навигация организована по задачам клиента: сайт, каталог, контент, продажи и настройки.
- Технические дочерние коллекции не занимают отдельные пункты навигации и редактируются внутри родительских сущностей.
- У первого экрана главной страницы существует один источник истины в Directus.
- Заголовок, описание, изображение, alt-текст и кнопки первого экрана редактируются без изменения кода.
- После сохранения опубликованных данных Directus фронтенд получает актуальные значения через контролируемую ревалидацию.
- Фронтенд не подменяет пустые или недоступные значения незаметными текстовыми либо графическими константами.
- Существующие данные сохраняются и мигрируются до скрытия или удаления дублирующих структур.

## Подтверждённые проблемы текущей реализации

1. В Data Studio отображаются 24 пользовательские коллекции одним плоским списком без групп.
2. Часть коллекций не имеет русского названия, а поля не имеют полезных пояснений и логической группировки.
3. Данные первого экрана хранятся в `page_sections`, хотя в схеме одновременно существует отдельная пустая коллекция `hero_blocks`.
4. Фронтенд не читает `hero_blocks`.
5. Изображение первого экрана жёстко задано в `HomeHero.tsx` как `/images/home/deere-shop-hero-v2.webp` и игнорирует `page_sections.image`.
6. При пустом заголовке или описании фронтенд показывает строки из кода, поэтому редактор не видит реальный результат своих действий.
7. Несколько выделенных коллекций (`hero_blocks`, `advantages`, `cta_blocks`, `banners`, `testimonials`, `seo_text_blocks`) не участвуют в текущем публичном чтении фронтенда либо дублируют поля основных сущностей.

## Выбранный подход

Использовать нативные возможности Directus 12.1.1: папки коллекций, singleton-коллекции, группы полей, понятные интерфейсы, шаблоны отображения и вложенное редактирование отношений. Отдельную кастомную админку не создавать.

Такой подход сохраняет обновляемость Directus и не превращает интерфейс клиента в дополнительное приложение, которое потребуется отдельно поддерживать.

## Навигация Data Studio

### Сайт

- `Главная страница` — singleton для управления всеми блоками главной.
- `Страницы` — информационные и юридические страницы.
- `Меню` — понятный список ссылок шапки, подвала и юридического меню.

### Каталог

- `Товары`.
- `Категории`.

Изображения, характеристики и документы товара открываются внутри карточки товара. Их таблицы остаются физическими дочерними коллекциями только там, где нормализованная структура полезна для API и масштабирования.

### Контент

- `Статьи`.
- `Вопросы и ответы`.
- `Недавние поставки`.

### Продажи

- `Заявки`.
- `Заказы`.

Позиции заказа открываются внутри заказа и не показываются отдельной коллекцией.

### Настройки

- `Настройки сайта` — singleton с данными компании, контактами, брендингом, подвалом, SEO по умолчанию и аналитикой.

### Скрытые технические коллекции

`page_sections`, `product_images`, `product_specifications`, `product_documents`, `order_items`, `contact_channels` и иные служебные структуры не выводятся отдельными пунктами основного меню, если редактор может безопасно работать с ними внутри родительской записи.

Скрытие не означает запрет редактирования или потерю функциональности. Оно означает перенос точки входа в понятную карточку родительской сущности.

## Модель главной страницы

Создаётся singleton `home_page` с русским названием `Главная страница`. Он является единой точкой входа редактора и содержит группы-аккордеоны.

### Основное

- Статус публикации.
- Включение страницы.
- Служебная дата обновления, доступная только для чтения.

### Первый экран

- `hero_title` — заголовок первого экрана, обязательное поле.
- `hero_text` — поясняющий текст, обязательное поле.
- `hero_image` — основное изображение, обязательное поле.
- `hero_image_alt` — осмысленное описание изображения, обязательное поле.
- `hero_primary_button_text`.
- `hero_primary_button_url`.
- `hero_secondary_button_text`.
- `hero_secondary_button_url`.
- `hero_search_placeholder`.

### Секции главной

Для каждой поддерживаемой секции хранятся как минимум:

- понятное название;
- переключатель показа;
- заголовок и вводный текст;
- порядок отображения, если секция допускает перемещение;
- связанные записи либо структурированный список элементов;
- подписи и URL кнопок, когда они есть в интерфейсе.

Состав первого релиза:

- категории;
- рекомендуемые товары;
- преимущества;
- этапы подбора;
- доверие к компании;
- недавние поставки;
- статьи;
- FAQ;
- контакты;
- форма заявки;
- финальный CTA;
- SEO-текст.

Для повторяемых небольших элементов используется дружественный интерфейс повторителя Directus. JSON-редактор с исходным кодом не показывается контент-менеджеру.

### SEO главной

- H1 при необходимости совпадает с `hero_title`, но хранится явно.
- SEO title.
- SEO description.
- canonical URL.
- Open Graph title, description и image.
- флаг индексации.
- структурированный SEO-текст.

## Минимизация коллекций

Минимизация проводится по пользовательскому интерфейсу и по модели данных, но без преждевременного удаления таблиц.

### Объединяются с основными сущностями

- Данные `hero_blocks` мигрируют в `home_page`, после чего коллекция архивируется и скрывается.
- SEO страницы хранится в `home_page`, `pages`, `categories`, `products` и `articles`; самостоятельная `seo_text_blocks` не используется для новых данных.
- Настройки CTA главной хранятся в соответствующей группе `home_page`; отдельная `cta_blocks` не используется для новых данных.
- Преимущества главной хранятся в повторителе или вложенной связи `home_page`; самостоятельный верхнеуровневый пункт `advantages` исчезает.
- Неиспользуемые `banners` и `testimonials` не показываются клиенту до появления реального сценария на фронтенде.

### Сохраняются как самостоятельные сущности

- товары и категории;
- страницы и статьи;
- FAQ, потому что вопросы могут связываться со страницами, категориями и товарами;
- заявки и заказы;
- недавние поставки;
- меню;
- глобальные настройки.

### Сохраняются как скрытые дочерние сущности

- изображения, характеристики и документы товаров;
- позиции заказов;
- каналы связи, если отношения удобнее единого JSON-поля.

## UX карточек

- Первые поля отвечают на вопрос «что это и опубликовано ли это»: название, статус, главное изображение.
- Поля собраны в раскрываемые группы: `Основное`, `Изображения`, `Характеристики`, `Продажи`, `SEO`, `Служебное`.
- Редко используемые SEO и служебные группы закрыты по умолчанию.
- ID, даты, источники импорта и другие технические поля скрыты либо доступны только для чтения.
- Поля шириной в половину строки используются только для логически связанных пар: цена и валюта, текст кнопки и ссылка.
- Статусы и варианты выбора имеют русские подписи.
- У каждого неоднозначного поля есть короткая русская подсказка с примером.
- Списки используют информативные шаблоны: товар показывает название, артикул, цену и статус; заявка — имя, телефон, источник и дату; заказ — номер, клиента, сумму и статус.
- В интерфейсе нет декоративных карточек и нестандартных визуальных решений, конфликтующих с нативным Directus. Основной ориентир — быстрое сканирование, предсказуемая форма и минимальное число переходов.

## Поток данных первого экрана

1. Редактор открывает `Главная страница → Первый экран`.
2. Меняет текст или изображение и сохраняет запись.
3. Directus сохраняет единственный объект `home_page`.
4. Flow или webhook Directus вызывает защищённый маршрут ревалидации Next.js с тегом главной страницы.
5. Серверный слой Next.js повторно читает `home_page`.
6. `HomeHero` получает нормализованный объект hero через props.
7. Изображение выводится через существующий защищённый media route и `next/image`.
8. После обновления страницы редактор видит те же опубликованные значения, которые находятся в Directus.

В компоненте hero не остаётся содержательных констант. Допускаются только технические значения оформления, не являющиеся контентом.

## Обработка ошибок

- Обязательные поля проверяются в Directus и в нормализаторе данных фронтенда.
- Если опубликованная главная не содержит обязательного hero-контента, сервер пишет структурированную ошибку, а страница показывает нейтральное диагностическое состояние без выдуманного рекламного текста.
- Если media-файл отсутствует или недоступен, используется явно обозначенный технический placeholder с пустым декоративным alt, а ошибка фиксируется в журнале. Placeholder не маскирует сохранённый редактором файл.
- Неполные необязательные кнопки не выводятся: текст и URL должны присутствовать парой.
- Черновые записи не попадают на публичный сайт.
- Webhook защищается отдельным секретом и принимает только известные коллекции и события.

## Миграция без потери данных

1. Создать `home_page` и интерфейсные метаданные без удаления существующих коллекций.
2. Перенести опубликованные значения hero из секции `page_sections` главной страницы, включая `image`.
3. Перенести заголовки, тексты, видимость и порядок остальных секций.
4. Сверить результат миграции с текущими опубликованными данными.
5. Переключить серверное чтение фронтенда на `home_page`.
6. Проверить редактирование текста, изображения, кнопок и видимости секций через живой Directus.
7. Скрыть прежние точки входа и пометить их как архивные.
8. Удаление физических коллекций рассматривать отдельным изменением только после периода стабильной работы и резервной копии.

## Права и автономность

- Контент-менеджер управляет главной, страницами, меню, статьями, FAQ, поставками, товарами и категориями.
- Менеджер продаж работает с заявками и заказами.
- SEO-менеджер редактирует SEO-группы основных сущностей, alt-тексты и внутренние ссылки.
- Администратор управляет ролями, аналитикой, webhook и служебными полями.
- Ограничение прав не должно создавать второй источник истины или требовать разработчика для штатного изменения контента.

## Проверка реализации

### Автоматические проверки

- Тест схемы проверяет русские названия, группы коллекций, hidden-флаги и singleton `home_page`.
- Тест метаданных проверяет группы полей, порядок, ширину, интерфейсы, подсказки и переводы вариантов.
- Тест миграции подтверждает перенос существующего hero без изменения текста и file ID.
- Тест серверного mapper подтверждает передачу hero title, text, image ID, alt и кнопок.
- Компонентный тест подтверждает использование CMS-изображения и отсутствие прежнего жёстко заданного пути.
- Тест ревалидации подтверждает обновление тегов главной после события Directus.

### Сквозная проверка

1. Изменить заголовок hero на уникальную контрольную строку в Directus.
2. Заменить hero image на контрольный файл.
3. Сохранить и опубликовать запись.
4. Открыть публичную главную страницу.
5. Подтвердить новый текст, новый file ID изображения, alt и отсутствие прежнего статического изображения.
6. Вернуть согласованный контент либо оставить новые клиентские значения по решению владельца.

### Проверка интерфейса

- Войти как контент-менеджер с языком `ru-RU`.
- Убедиться, что верхнеуровневая навигация соответствует пяти задачным группам.
- Открыть каждую видимую коллекцию и проверить русские подписи, подсказки, логичный порядок и отсутствие JSON-кода в штатных сценариях.
- Проверить клавиатурную навигацию, фокус, загрузку файлов и работу на ширине ноутбука.

## Ограничения первой итерации

- Не создаётся отдельное приложение-админка.
- Не добавляется произвольный конструктор новых типов секций. Клиент управляет предусмотренными секциями, их содержимым, связями, видимостью и порядком.
- Не удаляются таблицы до завершения миграции, резервного копирования и сквозной проверки.
- Не меняются реальные цены, артикулы и технические характеристики товаров.

## Итоговая пользовательская модель

Основной сценарий клиента должен укладываться в понятную цепочку:

`выбрать раздел → открыть содержимое → изменить понятное русское поле → сохранить → увидеть изменение на сайте`.

Если штатное изменение контента требует открыть исходный код, отредактировать JSON вручную, найти дублирующую коллекцию или дождаться разработчика, реализация не соответствует этой спецификации.
