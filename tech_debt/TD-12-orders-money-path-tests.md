# TD-12 — Заказы: тесты money-пути + батч-запись позиций (сегодня до 100 round-trip'ов на заказ)

- **Приоритет:** P2 (единственный money-модуль без тестов вообще; и по 1 HTTP-запросу на каждую позицию)
- **Усилие:** M (~0,5–1 день, TDD)
- **Тип:** tests + perf
- **Зависимости:** нет; CI (TD-01) желателен.

## Симптом и влияние

`frontend/src/lib/directus/orders.ts` — создание заказа в Directus — **не имеет ни одного теста**
(весь остальной data-слой покрыт: catalog.test.ts на 937 строк, leads/route.test.ts на 18 кейсов).
При этом:

- `orders.ts:61–75` — позиции заказа пишутся **последовательными** `POST /items/order_items`,
  по одному на строку корзины. Корзина до 100 строк → до 100 round-trip'ов + 100 шансов упасть
  посередине.
- Компенсация отказа (`orders.ts:66–86` и `api/orders/route.ts:59–84`): если позиция не записалась,
  заказ удаляется (каскад). Логика правильная, но ни разу не протестирована: в
  `app/api/orders/route.test.ts` всего 2 теста (лимит тела, проброс IP для Turnstile). Не покрыто:
  отказ item-write → compensating delete, 400-валидация, отказ Turnstile, снапшот-поля.
- `orders.ts:26–29` — `Number(total.toFixed(2))` округление суммы и снапшот-цены (`:66–71`) —
  арифметика денег без тестов.

## Решение (минимальное)

**Шаг 1 (TDD, до правок):** `frontend/src/lib/directus/orders.test.ts` по образцу соседних
(directusRequest мокается):

1. создаётся заказ с корректным payload (status, source, utm, consent-снапшот, page_url);
2. `total` = сумма позиций с округлением до 2 знаков (кейс с плавающей точкой: 0.1+0.2);
3. снапшот цены и title берутся из переданных строк, а не пересчитываются;
4. **компенсация:** мок, где второй POST `/items/order_items` падает → вызывается DELETE заказа;
5. все позиции пишутся с `order_id` созданного заказа.

Расширить `app/api/orders/route.test.ts`: 400-валидация (короткий телефон), отказ Turnstile → 503?/
(фактический код по route), успех → `{ order_id }`.

**Шаг 2 (батч):** заменить цикл POST'ов на один пакетный
`POST /items/order_items` с массивом тел (Directus поддерживает batch-массив в теле). Один запрос
вместо N; компенсирующий DELETE не меняется. Обновить тест 4: падение batch-запроса → DELETE заказа.

**Шаг 3:** фиксирующая проверка в API-роуте: количество позиций ≤ 100 уже ограничено схемой zod —
тестом подтвердить.

## Подводные камни

1. **Формат batch-запроса Directus:** массив объектов в теле `POST /items/order_items`
   (без обёртки `data` для REST v11+; сверить с фактическим поведением инстанса через
   `directus/client.ts`-паттерны или curl на dev-инстансе). Если инстанс требует `{ keys/... }` —
   писать как требует живой API, а не документация.
2. **Порядок позиций** в batch-ответе не гарантирован — тест не должен ассертить порядок массива,
   только состав (множество).
3. Каскадное удаление позиций в Directus должно касаться batch-записанных так же, как
   одиночных (внешний ключ ON DELETE) — проверить на dev-инстансе один раз вручную.
4. `Number(total.toFixed(2))` — типовая IEEE-754 ловушка: тест с 0.1+0.2 обязан зафиксировать
   текущее поведение (округление до 2 знаков), не «чинить» арифметику BigDecimal'ом.
5. Не выносить «транзакционность» в Directus Flow — компенсация остаётся на клиенте (анти-скоуп).
