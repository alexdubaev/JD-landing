# TD-19 — UTM-метки теряются при навигации: заявки приходят без источника

- **Приоритет:** P2 (требование AGENTS.md «UTM data in leads» молча нарушается на самом частом сценарии)
- **Усилие:** S (~3–5 ч с тестами)
- **Тип:** bug + tests
- **Зависимости:** после/вместе с TD-08 (`collectUtmAttribution` — туда встаёт persistence).

## Симптом и влияние

Все три формы читают UTM из `window.location.search` **в момент сабмита**:

- `frontend/src/components/forms/LeadForm.tsx:30`
- `frontend/src/components/cart/CheckoutForm.tsx:25`
- `frontend/src/components/forms/BulkPartsRequest.tsx:144`

Пользователь приходит по ссылке с `?utm_source=yandex&utm_campaign=...`, гуляет по каталогу
(каждый переход по внутренней ссылке уносит querystring), и заявка уходит **с пустыми utm-полями**.
В Directus-лидах источник теряется ровно у самых ценных сессий. Требование AGENTS.md
(«UTM data in leads», поля в схеме лида) выполняется только для отправки формы сразу с лендинга.

## Решение (минимальное)

1. `lib/analytics.ts` (рядом с `collectUtmAttribution` из TD-08):

   - `persistUtmOnce()`: на первом клиентском рендере (в `layout.tsx` или общем client-корне —
     там, где уже живёт Analytics-компонент) — если `location.search` содержит любые `utm_*`,
     записать их в `sessionStorage` под ключом `deere-shop:utm` (JSON, только непустые значения).
     Существующую запись **не перезатирать**, если новая пустая; перезатирать, если пришла новая
     метка (последний источник важнее).
   - `collectUtmAttribution()`: сначала текущий `location.search`, при отсутствии — значения из
     `sessionStorage`.

2. Серверная схема лида не меняется вообще (поля уже есть и валидируются) — правка чисто клиентская.

3. Тесты: `analytics.test.ts` — (а) persist при заходе с utm; (б) collect спустя «навигацию»
   (search пуст) возвращает сохранённые значения; (в) новый заход с другой меткой перезатирает;
   (г) без utm и без записи — пусто (лишние поля не шлются).

## Подводные камни

1. **Независимость от cookie-consent.** Место persist — рядом с `Analytics.tsx`, чей смысл —
   гейтить загрузку аналитики до согласия. `persistUtmOnce` обязан выполняться **независимо от
   consent**: это атрибуция полей формы лида (UTM пользователь сам принёс в ссылке), а не трекинг.
   Иначе для не согласившихся баг выживает. В коде — не вкладывать persist в consent-ветку.
2. **sessionStorage per-tab:** новая вкладка/окно = потеря метки. Для минимума приемлемо
   (большинство заявок — та же вкладка); если владельцу нужна межвкладочная атрибуция — это
   осознанное расширение до localStorage с TTL, отдельно.
3. «Перезатирать при новой метке» (last-click) — молчаливое продуктовое решение; при старте задачи
   дать владельцу подтвердить одной строкой (first-click vs last-click).
4. Не трогать `document.referrer`-выводы и не выдумывать utm_аналоги (gclid/yclid) — вне минимума;
   при желании фиксируется отдельно.
5. persist должен выполняться до первой отрисовки форм (компонент Analytics уже монтируется на
   всех страницах — рядом логично); иначе гонка «открыл форму до persist» — на практике невозможна
   (persist в том же commit-цикле), но тестом прикрыть.
6. `sessionStorage` недоступен (private mode) — обернуть в try/catch, молча деградировать
   (как cart-store).
7. Метрика (Yandex Metrica) живёт своей атрибуцией — не дублировать её логику, только utm-поля лида.

## Allowed files (ADR-002)

- `frontend/src/lib/analytics.ts` (+ `analytics.test.ts`)
- точечно: место монтирования persist (существующий `components/layout/Analytics.tsx` или
  `app/layout.tsx`) + тест при наличии.

## Верификация

1. `npm test`, typecheck, lint.
2. Ручной чек: открыть `/?utm_source=test`, пройти в каталог → в форму → отправить (DevTools:
   payload содержит utm_source=test); в прямой сессии без utm — поля отсутствуют, как раньше.

## Не делаем

- Никакой серверной атрибуции/cookie-модели, first/last-click параллельно, сбора gclid —
  при необходимости отдельная задача с владельцем маркетинга.
