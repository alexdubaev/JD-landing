# TD-11 — Устойчивость страниц: loading.tsx у продукта, отказоустойчивость каталога, hero без throw

- **Приоритет:** P2 (самая тяжёлая страница каталога — единственная без loading-скрина; главный блок умеет уронить всю главную)
- **Усилие:** S–M (~0,5 дня)
- **Тип:** bug / UX-consistency
- **Зависимости:** нет.

## Симптом и влияние

1. **Страница продукта** (`/catalog/[cat]/[product]`) делает 5 параллельных фечей
   (`page.tsx:85–90`) — и это единственная тяжёлая страница **без** `loading.tsx`: пользователь
   смотрит на пустоту до первого байда. Скрины есть у `/`, `/catalog`, `/catalog/[cat]`, `/articles`.
2. **Каталог-корень падает целиком**, если Directus недоступен: `catalog/page.tsx:70–74` зовёт
   `getCategories()` + `getPageSeoBySlug()` без try/catch → `error.tsx` (500-страница). При этом
   страница категории на тот же сбой отвечает деградацией: `catalog/[categorySlug]/page.tsx:99` —
   `.catch(() => [])`. Одна и та же зависимость — две политики.
3. **Главная роняется из-за hero**: `HomePageView.tsx:46` / `HomeHero.tsx:94–96` **бросают исключение**,
   если hero-контент в CMS неполон → вся главная уходит в `error.tsx`, хотя `app/page.tsx:86–109`
   аккуратно деградирует все остальные секции. Один кривой draft в `hero_blocks` = сайт «лежит».
4. Мелочь: `error.tsx:18` использует сырой `<div className="site-container">` вместо `<Container>`
   (все остальные state-страницы — через компонент).

## Решение (минимальное)

1. Скопировать 16-строчный `catalog/[categorySlug]/loading.tsx` в `catalog/[categorySlug]/[productSlug]/`.
2. В `catalog/page.tsx` обернуть получение данных в деградацию, как у страницы категории:
   категории → `[]` + статический фолбэк заголовка «Каталог продукции» (текст уже есть в инлайн-фолбэках
   файла), pageSeo → фолбэк-объект. Пустой каталог рендерит EmptyCatalog — приемлемая деградация
   (лучше пустая страница, чем 500).
3. HomeHero: вместо `throw` — рендер с фолбэк-значениями (существующие дифолты полей) +
   `console.warn("[home] incomplete hero block, rendering fallback")`. Проверить
   `HomePageView.tsx:46` — если там валидационный throw про отсутствие полей, заменить на
   `?? fallback`-цепочку.
4. `error.tsx` — заменить div на `<Container>` (импорт уже есть в проекте).

## Подводные камни

1. **Не превратить warn-деградацию в тихое проглатывание**: `console.warn` обязан остаться — иначе
   битый hero-контент в CMS никто не заметит (в Directus нет валидации полноты).
2. У HomeHero есть тест на mobile-границы (`Header.test`/`HomeHero`-смежные, коммиты
   `5ec32a2`, `ed871b7`) — при замене throw на фолбэки тесты «недостаточный контент → ошибка»
   (если есть) меняются на «недостаточный контент → фолбэк-рендер».
3. `force-dynamic` главной (page.tsx:29) не трогаем — причина документирована.
4. Захардкоженная метадата `articles/page.tsx:12–23` и инлайн-фолбэки текстов — **не** эта задача
   (см. stage-2 S-6, требует CMS-правок).
5. loading.tsx продукта должен совпадать по скелетону с категорийным (не рисуем новый дизайн).

## Allowed files (ADR-002)

- `frontend/src/app/catalog/[categorySlug]/[productSlug]/loading.tsx` (новый)
- `frontend/src/app/catalog/page.tsx` (+ тест на деградацию)
- `frontend/src/components/sections/HomeHero.tsx`, `frontend/src/app/HomePageView.tsx` (+тесты)
- `frontend/src/app/error.tsx`

## Верификация

1. `npm test`, typecheck, lint.
2. Локально с выключенным Directus: `/catalog` рендерит пустой каталог (не 500); главная рендерится
   с фолбэк-hero; в консоли сервера — warn.
3. `/catalog/tractors/xxx` показывает скелетон при медленном ответе (throttle в DevTools).

## Не делаем

- Не добавляем error-boundary на каждую секцию главной, не вводим Suspense-потоки, не делаем
  retry-логику фечей.
