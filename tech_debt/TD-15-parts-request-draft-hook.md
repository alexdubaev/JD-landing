# TD-15 — BulkPartsRequest (302 строки): вынести черновик в usePartsRequestDraft + фикс hydration-риска

- **Приоритет:** P3 (самый большой компонент; логика черновика нетестируема изолированно)
- **Усилие:** M (~0,5 дня)
- **Тип:** refactor
- **Зависимости:** после TD-10 (форма уже на едином сабмит-контракте).

## Симптом и влияние

`frontend/src/components/forms/BulkPartsRequest.tsx` — крупнейший компонент проекта (302 строки),
смешивает: персистенцию черновика в localStorage (`:70–73`, `:121–127`), синхронизацию со списком
подбора через CustomEvent (`:75–80`), хореографию фокуса/скролла (`:82–96`), валидацию файлов
(`:98–119`), сабмит с UTM (`:129–173`), экран успеха и приватный субкомпонент `Attachment`
(`:291–302`). Любая правка лид-пайплайна трогает этот файл.

Дополнительно — **риск hydration mismatch**: `initialDraft()` (`:47–50`) читает localStorage прямо в
`useState`-инициализаторе во время первого клиентского рендера, хотя сервер отрендерил `""`:
textarea получит отличное значение → React warning и принудительный перерендер.

## Решение (минимальное)

1. Новый `frontend/src/lib/leads/use-parts-request-draft.ts` (client-hook):
   - состояние черновика + `useEffect`-сиды из localStorage (устраняет mismatch: первый рендер —
     `""`, после монтирования — реальные данные);
   - запись в localStorage **с сохранением текущего поведения** (запись на каждое изменение —
     `:70–73`; дебаунс НЕ добавлять: меняет наблюдаемую персистенцию, выигрыш несуществен);
   - подписка/публикация CustomEvent синхронизации со списком подбора;
   - `clear()` (localStorage.removeItem + event).
2. Компонент остаётся владельцем UI: режимы (list/excel/photo), файлы, фокус, валидация, сабмит —
   на месте. Ожидаемый размер после: ~200 строк.
3. Тесты хука: изолированно с jsdom-localStorage — персистенция, синхронизация события, clear,
   **первый рендер без чтения storage** (assert: renderProbe показывает `""` до эффектов).

## Подводные камни

1. **Смена порядка:first-render пустой → эффект заполняет** — визуально мигание textarea на
   медленных устройствах. Приемлемо (сейчас — hydration warning, что хуже). Не «лечить» через
   `suppressHydrationWarning` на всём компоненте.
2. `reconcileProductRequestDraft` (`lib/leads/product-request-list.ts`) — общая с продуктным списком
   логика: хук зовёт её, не копирует.
3. Фокус-хореография зависит от момента применения черновика (пользователь добавил деталь из
   карточки → форма скроллится/фокусится). Изменение тайминга (эфект вместо render-init) может
   сместить скролл — проверить сценарий «добавил в подбор из каталога → открыл форму» вручную.
4. Не выносить валидацию файлов и Turnstile — это к форме, не к черновику.

## Allowed files (ADR-002)

## Верификация

1. `npm test`, typecheck, lint; в консоли dev-рендера страницы `/parts-request` нет hydration warning.
2. Ручной сценарий: черновик сохраняется между перезагрузками; «добавить в подбор» из карточки
   продукта появляется в форме; очистка после успешной отправки.

## Не делаем

- Не разбиваем компонент на N подкомпонентов, не строим state-machine (XState и пр.),
  не выносим файл-валидацию в «сервис загрузок».
