# TD-03 — /api/catalog/suggestions: без rate-limit и с неограниченной кардинальностью кэша

- **Приоритет:** P1 (единственный неаутентифицированный маршрут, фаналящий в Directus на каждый уникальный пользовательский ввод)
- **Усилие:** S (~2–4 ч с тестами)
- **Тип:** security / perf
- **Зависимости:** нет.

## Симптом и влияние

`GET /api/catalog/suggestions` — публичный поисковый autosuggest. Любой скрипер может долбить его
без лимитов; каждый уникальный префикс запроса создаёт запись в data-кэше Next (revalidate 60с) —
картinality не ограничена ничем. Плюс под капотом поиск по SKU вытягивает **всю таблицу продуктов**
(растёт с каталогом, цель проекта — 1000+ позиций).

## Доказательство (file:line)

1. `frontend/src/proxy.ts:18–25` — rate-limit-политики назначаются только на `POST /api/leads`,
   `POST /api/orders`, `POST /api/revalidate`. GET-запросы не лимитируются вообще. Роут
   `app/api/catalog/suggestions/route.ts` не имеет собственного лимита.
2. `frontend/src/lib/directus/catalog.ts:676–690` — `getCatalogSuggestions(query)` кладёт сырую
   пользовательскую строку в параметры феча → она становится частью ключа data-кэша Next
   (revalidate 60). Каждая уникальная строка от скрипера в 60-секундном окне — отдельный поход в
   Directus и отдельная кэш-запись: кардинальность ничем не ограничена (churn-нагрузка на Directus
   и память рантайма, а не монотонный рост).
3. `catalog.ts:600–615` — `resolveNormalizedSkuIds` тянет `fields: "id,sku", limit: "-1"` — всю
   опубликованную таблицу продуктов — и фильтрует на клиенте. Вызывается на каждой каталог-странице
   с поисковым запросом и на каждый free-text suggest.
4. `catalog.ts:681, 778` — `filter[id][_in]: matchedIds.join(",")`: широкий паттерн (например «50»)
   даёт мульти-КБ значение фильтра — риск лимита длины URL на прокси.

## Решение (минимальное)

1. **Rate-limit:** добавить в `proxy.ts` политику для `GET /api/catalog/suggestions`:
   `{ limit: 60, windowMs: 60 * 1000 }` — рядом с существующими, тот же `checkRateLimit`.
2. **Нормализация запроса до кэша:** в `getCatalogSuggestions` (и в `getCatalogPage` для `search`)
   нормализовать строку ключа: `trim().toLowerCase()`, обрезать до 64 символов (лимит длины в роуте
   уже 2–64). Нормализованная строка — в феч, сырая — только в логи. Это схлопывает вариации
   (`Трактор`, ` трактор `, `ТРАКТОР`) в один кэш-ключ.
3. **Кэп SKU-матчей:** в местах сборки `filter[id][_in]` ограничить `matchedIds.slice(0, 20)`.
   Suggest'у больше и не нужно.
4. В роуте `suggestions/route.ts` — прогонять query через ту же нормализацию до вызова либы
   (защита от вызова либы из другого места с сырой строкой).
5. **Тот же класс риска — `GET /media/[fileId]`** (`app/media/[fileId]/route.ts`): публичный
   проксирующий роут; каждый уникальный (в т.ч. фейковый) fileId = поход в Directus + кэш-запись
   (revalidate 300 / SWR 86400). Добавить политику для путей, начинающихся с `/media/`:
   `{ limit: 600, windowMs: 60 * 1000 }` — щедро (страница грузит десятки картинок; лимит обязан
   пропускать нормальное поведение и резать только скриперов-переборщиков id).

Полная замена full-scan на серверный поиск — **stage-2 (S-1)**, сюда не входит.

## Подводные камни

1. **Не сломать UX живого поиска:** 60 req/min/IP на автосабжест при дебаунсе ~300мс — запас
   трёхкратный; если в `HeroPartSearch` дебаунса нет — проверить и, при необходимости, это правка
   компонента (вне скоупа, зафиксировать в задаче как условие).
2. **Лимит `/media/` не должен ломать обычный browsing:** одна страница каталога тянет 20–50
   картинок, быстрое листание — сотни запросов в минуту. Перед фиксацией лимита замерить реальное
   число запросов на типичный заход (DevTools) и поставить лимит с 3–5-кратным запасом; 429 на
   картинку = сломанная страница. Альтернатива, если сомневаетесь: оставить `/media/` без лимита и
   завести отдельную задачу (не расширять эту).
3. Нормализация `toLowerCase` не меняет семантику поиска для RU (Directus `_contains` —
   case-insensitive для большинства конфигураций, но наши SKU-паттерны ASCII — безопасно).
4. `retryAfterSeconds` заголовок уже генерится общим кодом — не дублировать.
5. In-memory лимитер остаётся per-instance (один инстанс в текущем deploy — ок; multi-replica —
   stage-2 S-8).
