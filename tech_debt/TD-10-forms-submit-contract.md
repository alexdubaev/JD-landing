# TD-10 — Три формы заявки: единый контракт сабмита и ошибок (+ CheckoutForm не показывает ошибку сервера)

- **Приоритет:** P2 (пользовательский баг: заказ, отклонённый сервером, показывает безликое «не удалось»; три формы = три разных контракта)
- **Усилие:** M (~0,5–1 день)
- **Тип:** bug + refactor + tests
- **Зависимости:** после TD-08 (UTM-хелпер уже там) или вместе с ним.

## Симптом и влияние

На сайте три формы отправки лида/заказа — `LeadForm`, `CheckoutForm` (корзина), `BulkPartsRequest`
(подбор запчастей). Они копипастят общую логику сабмита, но контракт обработки ошибок у каждой свой:

- `LeadForm.tsx:52–57` — читает `body.error` от сервера и показывает его пользователю. ✅ правильно.
- `CheckoutForm.tsx:53–65` — при не-ok ответе **не читает тело**: `turnstile reset; setState("error")`
  → всегда безликое сообщение, причина (валидация? Turnstile? Directus?) скрыта. Пользователь не
  понимает, что исправить (например, «phone обязателен»).
- `BulkPartsRequest.tsx:~168–174` — читает `body?.error ?? fallback` (ок), но стейт-машина
  `"idle"|"sending"|"success"` не имеет состояния ошибки: ошибка живёт в отдельном `error`-стейте,
  и после неудачи `setState("idle")` — работает, но каждый следующий сабмит обязан вручную
  `setError(null)` — хрупко.

Плюс блок сбора UTM скопирован трижды (устраняется хелпером из TD-08 — здесь только подключение).

## Решение (минимальное)

1. Новый `frontend/src/lib/forms/useFormSubmit.ts` (client-hook, ~40 строк):

```ts
type SubmitState = "idle" | "sending" | "success" | "error";
function useFormSubmit() {
  const [state, setState] = useState<SubmitState>("idle");
  const [serverError, setServerError] = useState<string | null>(null);
  async function submit(fetchInit: () => Promise<Response | null>,
                        onSuccess: () => void): Promise<void> { … }
  return { state, serverError, submit, reset };
}
```

Семантика: `null`-ответ (сеть) → error с дефолтным текстом (передаётся per-form — у каждой формы
свой текст: «Не удалось отправить заявку…» / «Не удалось оформить заказ…» / «Не удалось отправить
список…»); не-ok → попытаться прочитать `body.error`, иначе дефолтный текст; ok → success.
`reset()` перед повторной отправкой.

2. Подключить хук во все три формы; разметку и специфичную логику (Turnstile reset, draft-clear,
   analytics-эвенты) оставить в формах через колбэки `onSuccess`/`onError`.
3. CheckoutForm дополнительно: показывать `serverError` в существующем error-блоке (разметка уже
   есть — туда просто приходит реальный текст).
4. Тесты: хелпер — юнит-тесты 4 веток (сеть-null, 400 c error, 400 без тела, 200); формы — по одному
   интеграционному тесту «сервер вернул 400 с error → текст отображён, кнопка снова активна»
   (LeadForm уже частично покрыт — добавить CheckoutForm и BulkPartsRequest).

## Подводные камни

1. **Не менять payload'ы** — серверные схемы (zod `.strict()`) чувствительны к лишним полям; хук не
   трогает FormData/JSON-сборку, только отправку и обработку ответа.
2. **BulkPartsRequest: очищать черновик только при успехе** (сейчас так и есть) — пронести через
   onSuccess, не «оптимистично».
3. `trackEvent`-вызовы (analytics) должны стрелять ровно там же, где сейчас (success-path) — тестом
   зафиксировать.
4. Turnstile reset — на любую неудачу (уже так в двух формах) — вынести в onError-колбэк формы,
   не внутрь хука (хук не знает про Turnstile).
5. React 19: хук с async-функцией в обработчике onSubmit — следить, чтобы `submit` не создавался
   заново каждый рендер без нужды (useCallback), иначе простые тесты «нажал — отправилось» могут
   гонять лишние ререндеры; не критично.
6. Honeypot `website` и consent-логику НЕ переносить в хук — они остаются в разметке форм.
